# 팀 인수인계

## 구조

| 경로 | 역할 |
|---|---|
| market.py | 로컬 HTTP 수신, SQLite, 호가·물량·시장 이력·개인 판매 메일 분석 |
| auto_update.py | 같은 포트에서 코드·웹 파일을 검증하고 교체, 실패 시 기존 화면 유지 |
| web/ | 한국어 화면. app.js와 app-v2.js는 같은 내용을 유지 |
| game_watch.py | 실제 Albion-Online.exe 실행 여부를 감시하고 소유한 수집기만 제어. 게임 중 분석 프로그램이 3회 연속 응답하지 않으면 다시 시작 |
| start.ps1 / stop.ps1 | 분석·수집 시작 및 소유 프로세스 종료 |
| enable-game-watch.ps1 | 현재 사용자 Windows 시작프로그램에 게임 감시 등록 |
| setup.py | 공식 수집기 다운로드, 숫자 품목 ID 갱신. 전용 수집기(`vendor/albiondata-client-fork.exe`)는 건드리지 않음 |
| (저장소 밖) albiondata-client 로컬 포크 | 전용 수집기 소스. 0.1.61 태그 기반, 빌드·변경 내용은 포크의 `FORK-LOCAL.md` |
| tests/ | 임시 데이터로 회귀 검증 |

## 협업 규칙

- main에 직접 덮어쓰기보다 작업 브랜치 → 테스트 → PR로 검토합니다.
- 실제 config.json, SQLite, 로그, 거래 CSV, 화면 캡처, 계정 정보는 커밋하지 않습니다. 필요한 예시는 합성 데이터로 만듭니다.
- 운영 DB·게임 프로세스·수집기를 테스트 대상으로 중단하거나 수정하지 않습니다.
- 서버는 loopback에만 바인딩하고 Host·Origin·로컬 UI 토큰 검증을 유지합니다.
- 호가 잔량, 구간 판매량, 내 완료 메일의 수량을 합산하거나 같은 지표로 부르지 않습니다.
- 새 세션의 일부 주문으로 이전 최저가를 무조건 덮어쓰지 않습니다. 단일 주문의 최저/최고 미확인 상태를 유지합니다.
- 게임 메일의 UnitPriceSilver는 이미 실버입니다. 라이브 호가의 10000배 단위와 다릅니다.
- 개인 메일은 캐릭터 식별 해시+메일 ID로 중복을 막습니다. 내용 충돌 시 합계에서 제외합니다. 메일은 24시간·요일별 시장 통계로 배분하지 않습니다. 판매 완료(`personal_sales`)만 판매 통계에 쓰고, 구매 주문 완료·만료와 판매 만료(`personal_mails`, kind `buy`/`buy_expired`/`sell_expired`)는 따로 보여 줍니다. `mailed`는 게임이 메일을 보낸 때(전용 수집기만 제공)입니다.
- 개인 자료(거래 메일, 내 주문 목록)는 private 경로로만 받습니다. `marketorders.mine`은 `/private/europe/`에서만 처리하고 `/ingest/europe/`에서는 무시합니다.
- 세후 실입금에 고정 세율 계산값을 사용하지 않습니다.
- 사서 되팔 때 수량 경고는 24시간·7일·28일 중 가장 느린 하루 판매량이 기준입니다(하루치 초과 '조금 위험', 3일치 초과 '위험'). 싹쓸이 분석은 '위험' 단계를 고르지 않으며, 본 매도 가격만 목표가로 씁니다.
- 거래 분석(지금 하세요·도시별·매매 후보·싹쓸이)은 설정의 `excluded_cities`(기본 Caerleon `3005`, Brecilien `5003`)를 사고파는 곳에서 모두 뺍니다. 시장 상세 시세와 수집은 그대로입니다.
- `book_stats`(10분 단위 호가 요약)와 `pick_log`(추천 기록, 30일)는 15분 유효 시간과 별개로 남습니다. 단일 선택 주문 응답은 `book_stats`에 넣지 않습니다.
- 지금 하세요는 `now_groups`(instant / wait)로 나뉘며 중복 제외는 같은 방식 안에서만 합니다. 기다리는 거래 수량은 `waiting_cap`(하루 판매량 기준과 `demand_outlook` 24시간 예상 중 작은 값)으로 제한합니다.
- 지금 하세요 순위는 확실성 가중치(바로 체결 1.0, 매도 주문 대기 0.7, 싹쓸이 0.5, 양쪽 주문 0.4), 7일 최고 구간 평균가 초과(×0.5), 레드존·안개 경유(×0.8)를 곱한 예상 이익으로 매깁니다. 같은 매도 목록·같은 구매자를 두 순위가 나눠 쓰지 않습니다.
- 매매 후보의 수수료는 방식별로 다릅니다. 바로 매입은 수수료 없음, 바로 판매는 판매세만, 주문 매입·주문 판매는 설정 수수료 포함. 단일 주문 수신·지난 호가는 어떤 방식에도 쓰지 않습니다.
- `my_orders`는 게임의 내 주문 목록에서 자동 등록(`source='auto'`)되거나 사용자가 입력한 내 주문입니다. 남은 수량은 시장 목록(`orders`)과 내 주문 목록(`remaining`/`checked`) 중 나중에 본 값을 씁니다. 같은 품목·도시·방향·가격에서 수량이 같거나 적은 관측 주문 번호에 한 번만 연결하고(같은 수량 우선), 남은 수량·체결은 `orders`·`order_fills`에서 읽습니다. `waiting_cap`은 내 남은 수량을 빼고, 내 매도가보다 싸게 올리는 추천은 ×0.7과 경고, 싹쓸이는 내 매물을 사지 않습니다.
- 화면 수정 시 스크롤 위치·표 내부 스크롤·설정 입력 보존을 확인합니다.
- API build와 프런트 버전 검사를 함께 갱신합니다. 핵심 원리 변경 시 관련 회귀 검증을 유지합니다.

## 다음 계획

2. (완료) 전략 연구 탭.
3. 지난 4주 모의 실험: 시장별로 A(평일 매수 주문으로 모아 주말에 매도), B(얇은 시장에서 최저가를 서서히 올리기), C(조금씩 사고 최저가 근처에 수요만큼 나눠 걸기)의 이익과 안정도 별점 비교. 주말 표본이 4번뿐이라 처음엔 참고용으로 표시.
4. 주문 넣고 기다리기 추천에 6시간(최선)·하루(괜찮음)·3일(최대) 안정도 별점 수량. ★5 = 기간 안에 다 팔 확률 90% 이상, ★4 80%, ★3 70%, ★2 60%, ★1 그 미만. 내 몫 = 기간 내 즉시 구매 수요 − 앞선 매물 − 새로 끼어들 더 싼 매물. 시간대별 분할 매수·매도 안내 포함.
5. (전용 수집기로 해결, 실제 게임 확인 중) 메일과 내 주문.
   - 원인(2026-10-26 실제 패킷·디버그 기록으로 확인): ① 게임 업데이트로 우편함 목록(174)의 자료 위치가 3·7·11·12(메일 ID `[]int32`, 위치, 종류, 보낸 시각 .NET 틱 `[]int64`)로 바뀌었는데 0.1.61은 3·6·10·11을 읽어 매번 '150 error(s) decoding'이 나고, 그래서 모든 메일이 'Mail Info is not valid'로 버려졌습니다. ② 주문 목록 응답은 디버그 메시지 자리에 문자열 배열이 오고 그 뒤 파라미터 표에 진짜 작업 번호가 있는데, 0.1.61은 표를 버리고 모두 GetOffers(81)로 바꿨습니다. 그래서 내 주문(94)과 완료된 거래(89) 목록까지 공개 시장 자료로 올라갔습니다. ③ 게임의 '내 주문' 탭은 92·93이 아니라 94(GetMyOpenAuctions)를 두 번 요청합니다. 응답 파라미터 2가 1이면 매도, 2면 매수 목록입니다. 주문의 `LocationId`는 null이고, 목록은 지금 있는 시장의 주문만 담습니다.
   - 전용 수집기(로컬 포크, `vendor/albiondata-client-fork.exe`, start.ps1이 있으면 사용): 판매 완료·판매 만료·구매 주문 완료·구매 주문 만료 메일을 `marketnotifications`(NotificationType으로 구분)로, 내 주문 목록을 `marketorders.mine`(`Kind`, `LocationId`, `Orders`)으로 private 경로에만 보냅니다. 수신기는 `ingest_my_orders`→`sync_my_orders`로 바로 처리하고, 50개 미만 목록이면 그 도시·종류에서 빠진 주문을 정리합니다(빈 목록 포함).
   - 공식 수집기 대체 수단: start.ps1 인자는 `-debug -operations 81,82,94,174,175,176 -events 65535`. `read_client_log`가 94 요청 뒤, 81·82 요청 전(120초 이내)에 온 시장 자료를 내 주문으로 처리합니다. 로그 첫 줄의 버전에 `-local`이 있으면(전용 수집기) 이 방식은 쓰지 않습니다.
   - 판매·구매 만료 메일 본문 순서(`거래 수량|주문 수량|실버|품목|`)는 이 PC 우편함에 견본이 없어 AlbionDataAvalonia 문서의 실제 견본을 따랐습니다. 첫 만료 메일을 열면 '메일 수집 진단'에서 결과를 확인해야 합니다.

## 현재 검증 상태

2026-10-25 1차 소스 기준 합성 단위·회귀 검사 77개 통과, 운영 DB 읽기 전용 복제 점검 207개 통과. 화면의 가격·수량 분리, 내 메일 표시, 바로가기, 넘침·콘솔 오류를 검증했습니다. 저장소에는 실제 DB·검증 화면·로컬 보고서를 포함하지 않습니다.

2차 변경(오늘 도시별 정리, 바로 매입·판매 계산, 감시 상태 표시, 분석 프로그램 재시작, Node 선택화)은 합성 단위·회귀 검사 87개 통과(Linux, Windows 전용 1개 생략)와 합성 자료 데스크톱·모바일 화면 확인까지 진행했습니다. Windows에서의 PowerShell 스크립트 변경, 실제 게임 패킷, 운영 DB 복제 점검(`debug_market.py`)은 아직 실행하지 않았습니다.

3차 변경(사서 되팔 때 수량 경고, 매물 싹쓸이 분석)은 합성 단위·회귀 검사 91개 통과(Linux, Windows 전용 1개 생략)와 합성 자료 데스크톱·모바일 화면 확인까지 진행했습니다. 실제 게임 매도 목록으로 계산한 비용·단계는 아직 대조하지 않았습니다.

4차 변경(지금 하세요 1·2·3순위, 한 거래 예산 설정, 탭 화면, 메일 수집 진단과 전체 메일 목록)은 합성 단위·회귀 검사 99개 통과(Linux, Windows 전용 1개 생략)와 합성 자료 화면 확인까지 진행했습니다. 사용자가 게임에서 판매 완료 메일을 열었는데 저장되지 않았다는 보고가 있어 진단을 추가했으며, 실제 원인은 진단 결과로 확인해야 합니다.

5차 변경(전용 수집기 지원: 메일 4종, 내 주문 개인 토픽, 공식 수집기 대체 경로 94번)은 합성 단위·회귀 검사 123개 통과(Windows)와, 포크 Go 테스트(합성 자료) 통과까지 진행했습니다. 녹화한 실제 게임 패킷을 포크 디코더로 재생해 '내 주문' 목록(매수 3·매도 3)이 게임 화면과 같고, 메일 3개(판매 완료 2, 구매 주문 완료 1)의 도시·품목·단가·수량이 해석되는 것을 확인했습니다. 실제 게임에서 포크→수신기로 저장되는 것과 만료 메일 2종은 PR 설명의 확인 결과를 보세요. 수집기 인자를 바꾼 경우 다음 수집기 실행에서 적용됩니다.

스크린리더 전체 동선, 모든 확대 배율·모바일 화면은 추가 검증 대상입니다. 같은 가격 정보가 반복되는 구역은 향후 접기 기능 등을 검토할 수 있습니다. GitHub 자동 다운로드·배포 기능은 없습니다.

Windows Python 3.11+ / Node 22+ / tzdata. 분석 수식·수신 로직은 임시 Store로 확인하고, UI는 별도 포트와 합성/허용된 복제 자료로 검증합니다. 주의: app.js와 app-v2.js의 불일치를 만들지 않습니다.
